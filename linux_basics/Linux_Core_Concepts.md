## 1. Linux in the Real World: Distributions

Linux is the kernel; a **distribution (distro)** packages it with tools, a package manager and defaults. Teams choose a distro for stability, support and ecosystem.

| Family | Examples | Package tools | Typically chosen for |
| :--- | :--- | :--- | :--- |
| **Debian family** | Debian, Ubuntu | `apt`, `dpkg` | Developer-friendly, huge package catalog, very common in the cloud |
| **Red Hat family** | RHEL, CentOS, Rocky, Fedora | `dnf` / `yum`, `rpm` | Enterprise stability, long-term support, corporate certification |

A typical application's journey often looks like this:

1. **Physical or on-premise servers** in a company data center
2. **Cloud virtual machines** (AWS EC2, Google Compute Engine, Azure VMs)
3. **Containers and microservices** (Docker)
4. **Kubernetes clusters** that orchestrate those containers

Linux sits underneath every one of these stages, which is why understanding it deeply pays off.

### Identify your own system

```bash
cat /etc/os-release   # distribution name, version, family
hostnamectl           # hostname, OS, kernel, architecture, virtualization
uname -a              # kernel and architecture summary
whoami                # current user
```

## 2. The Linux Kernel

The **kernel** is the core of the operating system. It sits between hardware and the programs you run, managing resources as efficiently and fairly as possible.

### The librarian analogy

| Library | Linux |
| :--- | :--- |
| Librarian | **Kernel** |
| Books, DVDs, workstations (limited) | **Hardware**: CPU, RAM, disks |
| Students | **Applications and processes** |

Without a librarian, students would grab whatever they could, nobody would track who has what, and resources would run out. The librarian hands out resources fairly, keeps track, and gets them back. The kernel does the same for processes.

### The four jobs of the kernel

1. **Memory management**: tracks what memory is used, by whom, and where.
2. **Process management**: decides which process gets the CPU, when, and for how long.
3. **Device drivers**: act as interpreters between hardware and processes.
4. **System calls and security**: receive requests from processes and enforce permissions.

### Monolithic yet modular

- **Monolithic**: the kernel performs scheduling, memory management and much more by itself, in one privileged program.
- **Modular**: it can load and unload **kernel modules** (`.ko` files) while running, without a reboot.

### Kernel versions

```bash
uname -r
# Example output: 5.15.0-72-generic
```

| Part | Example | Meaning |
| :--- | :--- | :--- |
| Kernel version | `5` | Main version |
| Major revision | `15` | Major revision |
| Minor revision | `0` | Minor revision |
| Patch level | `72` | Patch or build number |
| Suffix | `generic` | Distribution-specific information |

Linux was created by Linus Torvalds in 1991. The source and the latest releases are at [kernel.org](https://kernel.org).

```bash
uname -a            # full kernel and architecture info
cat /proc/version   # kernel build details (a virtual file generated by the kernel)
```

## 3. Kernel Space, User Space and System Calls

Memory is split into two areas:

| | Kernel space | User space (userland) |
| :--- | :--- | :--- |
| Runs | The kernel, its extensions, most device drivers | All your programs: Bash, Firefox, Python, Java, etc. |
| Access | Unrestricted access to hardware | Restricted access to CPU and memory |
| Analogy | The staff-only area of the library | The reading area for students |
| CPU privilege | Ring 0 | Ring 3 |

This separation means a crashing application cannot take the whole system down.

### System calls

A program in user space cannot touch hardware directly. It makes a **system call** (syscall) asking the kernel to do it. Examples: `open`, `read`, `write`, `close`, `getpid`. For instance, `cat /etc/os-release` triggers an `open` syscall, then `read`, then `close`.

You can watch syscalls with `strace` (you may need to install it):

```bash
strace ls               # every syscall made by ls
strace -c ls            # summary count of syscalls
```

## 4. How Linux Detects Hardware

When you plug in a device, for example a USB disk:

1. The **device driver** in kernel space notices the change and generates a **uevent**.
2. The user-space device manager **`udev`** receives the event.
3. `udev` creates a **device node** in `/dev` (for example `/dev/sdb1`).

The disk is now visible to the system.

Two helpful tools:

```bash
udevadm info /dev/sda    # query the udev database about a device
udevadm monitor          # watch uevents live (plug or unplug something!)
```

## 5. Inspecting Hardware from the Command Line

### Kernel messages: `dmesg`

The kernel keeps hardware and driver messages in an in-memory **ring buffer**. `dmesg` displays them.

```bash
dmesg | less
dmesg | grep -i usb
dmesg | tail -n 25
```

On many modern systems, regular users are not allowed to read it; use `sudo dmesg`.

### PCI devices: `lspci`

Lists network cards, graphics cards, RAID controllers and other devices attached to the motherboard's PCI bus.

```bash
lspci
lspci -v     # more detail
```

### Storage devices: `lsblk`

```bash
lsblk
lsblk -f     # include filesystems and UUIDs
```

Example reading: `sda` is the whole physical disk (type `disk`); `sda1`, `sda2` are partitions carved from it (type `part`).

The **MAJ:MIN** column shows two numbers:

- **Major** (left): the driver type. `8` means SCSI/SATA-style disk.
- **Minor** (right): which device or partition. `sda` is `8:0`, `sda1` is `8:1`, and so on.

### CPU: `lscpu`

```bash
lscpu
```

Key fields:

| Field | Meaning |
| :--- | :--- |
| Architecture / CPU op-mode(s) | 32-bit or 64-bit |
| Socket(s) | Physical CPU slots |
| Core(s) per socket | Cores in each CPU |
| Thread(s) per core | Threads each core runs at once |
| CPU(s) | Total virtual CPUs |

**Total vCPUs = sockets × cores per socket × threads per core.** Example: 1 × 4 × 2 = **8**.

**32-bit vs 64-bit:**

| | 32-bit | 64-bit |
| :--- | :--- | :--- |
| Addressable values | 2³² | 2⁶⁴ |
| Max RAM | 4 GB | About 18 exabytes (theoretical; limited by the OS in practice) |
| Can run | 32-bit OS and software only | 64-bit **and** 32-bit software (64-bit recommended) |

### Memory: `free` and `lsmem`

```bash
free -h              # human-readable (add -m for MB, -g for GB)
lsmem --summary      # total online memory
lsmem                # detailed memory blocks
```

### Everything at once: `lshw`

```bash
sudo lshw -short     # concise hardware inventory
```

Without `sudo`, `lshw` warns that its output may be incomplete or inaccurate.

## 6. Running Commands as Root with `sudo`

Not every user may run every command. Some tasks, like hardware inspection or installing software, require **root** (superuser) privileges. Prefix the command with `sudo`:

```bash
sudo lshw -short
```

- You are asked for **your own** password, not root's.
- Administrators control who may use `sudo` and which commands they may run, and the activity can be logged.
- Use it only when needed. Root can change or delete anything.

(Configuring `sudo` is covered in a later module.)

## 7. The Boot Sequence

You can start the boot process by powering on a stopped machine or by rebooting a running one. It has four stages:

| # | Stage | What happens |
| :--- | :--- | :--- |
| 1 | **BIOS/UEFI POST** | The firmware runs a **Power-On Self-Test** to check the hardware. If it fails, the boot stops. |
| 2 | **Bootloader (GRUB2)** | Firmware runs boot code from the boot device. GRUB2 (Grand Unified Bootloader v2, files in `/boot`) shows a menu if you have several operating systems (dual boot), loads the chosen kernel and passes it parameters. |
| 3 | **Kernel initialization** | The compressed kernel is decompressed into memory, initializes hardware and memory management, mounts the root filesystem, and starts the first process. |
| 4 | **Service initialization (systemd)** | The init system mounts filesystems and starts services until the machine is usable. |

### PID 1 and init systems

The first user-space process is given **process ID 1**. It is the ancestor of all other processes.

| | SysV init (legacy) | systemd (modern standard) |
| :--- | :--- | :--- |
| Startup | Sequential, using scripts in `/etc/init.d/` | Parallel, which gives faster boots |
| Seen in | RHEL/CentOS 6 and older | Ubuntu, Debian, RHEL 7+ and most current distros |

Check which one you have:

```bash
ls -l /sbin/init
# On systemd systems it points to /lib/systemd/systemd
```

Explore your own boot:

```bash
systemd-analyze                    # total boot time (kernel + userspace)
systemd-analyze blame | head -n 10 # slowest services
journalctl -b                      # logs from the current boot
journalctl -b -p err               # only errors
```

## 8. Runlevels and systemd Targets

A **runlevel** (operating mode) defines which services are running.

| Runlevel | systemd target | Mode |
| :--- | :--- | :--- |
| 0 | `poweroff.target` | Halt / power off |
| 1 | `rescue.target` | Single-user maintenance |
| 3 | `multi-user.target` | Multi-user, command line only (typical for servers) |
| 5 | `graphical.target` | Multi-user with graphical interface (typical for desktops and laptops) |
| 6 | `reboot.target` | Reboot |

A graphical target needs a display manager service running; the multi-user target does not, which saves CPU and RAM.

### Inspect and change the mode

```bash
runlevel                 # e.g. "N 5": no previous level, currently 5
systemctl get-default    # graphical.target or multi-user.target
ls -l /etc/systemd/system/default.target   # a symlink to the chosen target file

sudo systemctl set-default multi-user.target   # boot to command line from now on
sudo systemctl set-default graphical.target    # boot to GUI from now on
sudo systemctl isolate multi-user.target       # switch right now, no reboot
```

`set-default` takes effect at the **next boot**. `isolate` switches immediately and stops services that don't belong to the new target, so save your work first.

> ⚠️ Only set `graphical.target` as default if a desktop environment is actually installed.

```bash
systemctl list-unit-files --type=target   # all available targets
```

## 9. File Types

> **"Everything is a file."** Documents, directories, disks, keyboards and communication channels are all represented as entries in the filesystem and accessed in similar ways.

### The seven types

The first character of `ls -l` output tells you the type:

| Char | Type | Description | Example |
| :--- | :--- | :--- | :--- |
| `-` | Regular file | Text, scripts, images, programs | `/etc/os-release` |
| `d` | Directory | A file that lists other files | `/home` |
| `l` | Symbolic link | A pointer (shortcut) to another path | `/bin/sh` on many systems |
| `c` | Character device | Serial, unbuffered devices | `/dev/null`, `/dev/tty` |
| `b` | Block device | Devices read and written in blocks | `/dev/sda` |
| `s` | Socket | Endpoint for two processes to communicate | |
| `p` | Named pipe (FIFO) | One-way channel from one process to another | |

Regular files, directories and "special" files (everything else) are the three broad groups.

### Identify a file's type

```bash
ls -l /dev/null          # starts with c
ls -ld /home             # starts with d
file /bin/bash           # inspects the contents, not just the name
file /etc/os-release
```

### Links

| | Symbolic (soft) link | Hard link |
| :--- | :--- | :--- |
| Create | `ln -s target linkname` | `ln target linkname` |
| What it is | A small file holding the path of another file; like a Windows shortcut | Another **name** for the same data on disk |
| Delete the original | The link breaks ("dangling") | The data survives; the other name still works |
| Delete the link | Original is untouched | Data is only freed when the **last** name is deleted |
| Limits | Can point across filesystems and to directories | Same filesystem only |

```bash
touch test_doc.txt
ln -s test_doc.txt test_symlink.txt
ls -l test_doc.txt test_symlink.txt    # symlink shows l and ->
rm test_doc.txt test_symlink.txt
```

## 10. The Filesystem Hierarchy

Windows uses separate drive letters (`C:`, `D:`). Linux has **one tree** starting at the root directory `/`. Every disk, partition or USB stick is **mounted** onto a folder in that tree.

| Directory | Purpose |
| :--- | :--- |
| `/` | Root; parent of everything |
| `/home/<user>` | Users' personal files |
| `/root` | Home directory of the root user |
| `/bin`, `/sbin` | Essential commands (`cp`, `mv`, `mkdir`, `date`) for users and administrators |
| `/etc` | System-wide **configuration files** |
| `/opt` | Optional third-party or custom software (e.g. a company web application) |
| `/mnt` | Mount point for filesystems you mount **manually**, usually temporarily |
| `/media` | Where removable media (USB drives) are mounted **automatically** |
| `/tmp` | Temporary files; often cleared on reboot |
| `/dev` | Device files for hardware |
| `/lib`, `/lib64` | Shared libraries used by programs in `/bin` and `/sbin` |
| `/usr` | Installed user applications and their data (`/usr/bin`, `/usr/lib`) |
| `/var` | Variable data that grows: **logs** (`/var/log`), caches, mail |
| `/proc` | Virtual files exposing kernel and process information |

> On many modern distros `/bin`, `/sbin` and `/lib` are symlinks into `/usr`. You can see this with `ls -l /`.

### Example workflow

Installing software from a network share: mount it temporarily on `/mnt`, copy the installer to `/tmp`, install, unmount `/mnt`, delete the temp files. Plug in a USB drive and it appears under `/media`.

### Checking disk space

```bash
df -h            # every mounted filesystem: size, used, available, mount point
df -h /          # just the filesystem holding /
df -hT           # also show filesystem type
du -sh ~         # how much space your home directory uses
du -sh /var/log  # how much space the logs use
```

### Mounting by hand

```bash
sudo mount /dev/sdb1 /mnt
sudo umount /mnt
```

Troubleshooting tip: when something goes wrong with a system or application, look in `/var/log` first.

## 11. Final Practice Lab

**Part A: Know your system**

1. Run `cat /etc/os-release` and `hostnamectl`. Which distro family is it?
2. Run `uname -r`. Write down each part of the version number.
3. Run `whoami`, then `echo $SHELL`.

**Part B: Hardware**

4. Run `free -h` and `lsmem --summary`. How much RAM do you have?
5. Run `lscpu`. Calculate the total vCPUs (sockets × cores × threads) and compare with the `CPU(s)` field.
6. Run `lsblk`. Identify the disk and its partitions and read the MAJ:MIN numbers.
7. Run `lspci` and find your network or graphics device.
8. Run `sudo dmesg | tail -n 20`.
9. Run `sudo lshw -short`, then run `lshw -short` without sudo and compare the warnings.

**Part C: Boot and run modes**

10. Run `ls -l /sbin/init`. Is your system using systemd?
11. Run `systemd-analyze` and `systemd-analyze blame | head -n 10`.
12. Run `journalctl -b -p err`.
13. Run `runlevel` and `systemctl get-default`, then `ls -l /etc/systemd/system/default.target`.

**Part D: File types and the hierarchy**

14. Run `ls -l /dev/null` (should start with `c`) and `ls -l /dev/sda*` or `/dev/nvme*` (should start with `b`).
15. Run `file /bin/bash`, `file /etc/os-release`, `file /dev/null`.
16. Create a file and a symbolic link, inspect them with `ls -l`, then delete them.
17. Create a hard link: `touch a.txt && ln a.txt b.txt`, then run `ls -li a.txt b.txt`. Both names show the **same inode number**. Delete `a.txt` and confirm `b.txt` still works. Clean up.
18. Run `ls -l /` and match each directory to the table in section 10.
19. Run `df -h`, then `du -sh ~`.
20. Run `ls -l /var/log`.
